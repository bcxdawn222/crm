## 三、安全和运维问题

### P0：需要尽快处理

#### 1. 没有发现数据库备份

在常见备份目录中没有发现 SQL、SQL.GZ 或数据库 dump 文件，也没有发现包含 MySQL、MariaDB、CRM、backup 或 dump 的定时任务。

建议：

- 每天执行数据库全量备份。
- 备份文件保留至少 7 个每日版本和 4 个每周版本。
- 备份保存到服务器之外的对象存储或另一台机器。
- 定期执行恢复演练，不能只确认备份文件存在。
- 在修改表结构或上线重要版本前额外生成一次备份。

#### 2. 应用进程以 root 用户运行

PM2 和 Next.js 进程当前以 `root:root` 身份运行。应用漏洞、依赖漏洞或文件上传问题可能因此获得过高的系统权限。

建议创建独立的低权限系统用户，例如 `crm-app`，只授予应用目录、日志目录和必要运行资源的访问权限，再由该用户运行 PM2。

#### 3. 已共享的 SSH 密码需要更换

本次远程校验使用了用户在会话中提供的 SSH 密码。该密码不应继续作为长期生产凭据。

建议立即更换该密码，并改用 SSH 密钥登录；完成密钥验证后关闭 root 密码登录，保留受控的提权方式。

### P1：建议安排整改

#### 4. MariaDB 监听所有网卡

MariaDB 当前在 `0.0.0.0:3306` 和 `[::]:3306` 监听。外部 TCP 测试无法连接 3306，说明外围防火墙或云安全组当前阻断了公网访问，但数据库自身仍未限制监听地址。

建议将 MariaDB `bind-address` 设置为 `127.0.0.1`。同时继续保持云安全组不开放 3306，形成两层限制。

#### 5. 应用数据库账号权限过大

`crm_app@127.0.0.1` 当前拥有 `crm_system.*` 的 `ALL PRIVILEGES`。普通应用运行通常不需要随时具备建表、删表、授权等全部权限。

建议拆分：

- 运行账号：仅保留日常查询和业务写入需要的权限。
- 迁移账号：仅在部署执行 `prisma migrate deploy` 时临时使用，部署完成后不供应用进程使用。

#### 6. 没有业务审计表

数据库中未发现 `AuditLog`、`OperationLog` 或 `AuditEvent` 等审计表。当前无法在数据库层面追溯客户负责人变更、公海认领、合同版本、订单金额、回款和文件下载等关键操作。

建议增加统一审计模型，记录操作人、对象类型、对象 ID、动作、变更前后摘要、请求来源、时间和结果。审计记录不应保存密码、token 或完整敏感正文。

### P2：进一步加强

#### 7. 数据库恢复能力有限

- MariaDB 二进制日志 `log_bin` 当前关闭，不能基于 binlog 进行时间点恢复。
- `local_infile` 当前开启，若应用或数据库账号被滥用，会增加本地文件导入风险。
- `require_secure_transport` 当前关闭。应用目前使用本机连接，短期影响较小，但不适用于未来跨主机连接。

建议在完成全量备份和恢复演练后，再评估开启 binlog；无业务需要时关闭 `local_infile`。如果未来数据库跨主机部署，应启用 TLS 并强制安全传输。
