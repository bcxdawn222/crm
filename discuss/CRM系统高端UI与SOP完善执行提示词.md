# CRM系统高端 UI 与 SOP 完善执行提示词

请把当前项目当成一个已经上线、正在被销售团队使用的销售 CRM 系统进行审查和改造。不要把它当成空白项目重新设计，也不要凭空增加一套新的客户字段。所有改动必须优先复用当前代码、数据库模型、页面路由和权限体系。

## 一、你的工作角色

你同时承担以下角色：

- 资深产品经理：先理解销售团队的真实工作流程，再决定页面和功能如何调整。
- B2B CRM 交互设计师：参考纷享销客、销售易、悟空 CRM、Zoho CRM、HubSpot、Pipedrive 等成熟销售 CRM 的信息架构、信息密度、工作台、列表、详情和时间线设计。
- 高级前端工程师：在现有技术栈内完成有质量的 UI 重构，不做只停留在视觉层的假改造。
- 后端与数据安全工程师：保证每个业务接口都有认证、权限、数据范围、输入校验和错误处理。
- 测试工程师：自主启动、测试、复现问题、修复问题并再次验证，不能只凭代码阅读判断功能可用。

## 二、当前项目事实

当前项目技术栈：

- Next.js 14
- React 18
- TypeScript

- MySQL
- NextAuth

## 三、总体目标

把当前系统完善成一个视觉更成熟、使用更顺手、业务流程更完整、数据更安全的销售 CRM：

1. 保留现有字段、数据和业务入口，不破坏历史数据。
2. 让销售人员进入系统后能快速看到客户、待跟进事项、逾期提醒和近期业务变化。
3. 让销售主管能看清团队客户归属、跟进质量、公海流转、合同订单和回款情况。
4. 让财务人员能安全查看和维护合同、订单、回款及发票信息。
5. 让管理员能维护用户、角色、权限和系统配置，并且所有高风险操作可追溯。
6. 让系统具备专业的销售 SOP，但不扩展为 ERP、财务总账、项目管理或低代码平台。

## 四、UI 设计方向

### 4.1 设计定位

Reading this as: 面向销售团队的 B2B CRM 工作台，采用专业、克制、可信、信息清晰的企业软件设计语言，参考成熟 CRM 的工作台和数据管理方式，但不复制任何品牌的 Logo、配色、文案、素材或页面结构。

设计参数：

- `DESIGN_VARIANCE: 4`
- `MOTION_INTENSITY: 3`
- `VISUAL_DENSITY: 6`

### 4.2 视觉要求

- 以专业企业软件为目标，不使用廉价渐变、紫色 AI 光晕、堆叠玻璃卡片、夸张动画或营销官网式大标题。
- 使用稳定的中性色基础，加一个明确的品牌强调色；状态颜色只用于状态表达，不作为装饰。
- 优先使用清晰的层级、间距、边框、表格分组和留白体现高级感，不靠大量阴影和圆角。
- 保持统一的圆角、按钮高度、表单间距、表格行高、标签样式和图标风格。
- 图标优先复用项目已有图标库或 Ant Design 图标，不手写 SVG。
- 保持中文界面的专业性，按钮和字段名称使用真实销售业务语言，不使用“开始探索”“解锁增长”等营销文案。
- 所有页面必须有加载、空数据、错误、无权限、保存中、保存成功和保存失败状态。
- 所有表格必须考虑窄屏适配、横向滚动、固定关键列、批量操作和字段可见性。
- 不用卡片套卡片；仪表盘指标、表格和详情区域优先使用分区、分割线和紧凑布局。
- 颜色、文字和按钮必须通过对比度检查，不能出现白底白字、浅灰字难以阅读或状态颜色无法区分的情况。

### 4.3 页面重点

#### 首页工作台

- 首屏展示今日待办、逾期跟进、即将到期合同、本月订单、本月回款、客户数量和公海待领取数量。
- 每个指标必须能点击进入对应列表，并自动带上正确筛选条件。
- 展示近期客户跟进、合同到期、回款和公海流转动态。
- 销售人员看到本人范围，主管看到本人及下属范围，财务看到财务相关范围。
- 图表必须有明确的时间范围、统计口径和空数据提示。

#### 客户列表

- 顶部提供搜索、筛选、保存筛选、重置筛选和新增客户。
- 保留现有客户字段，不强行增加没有数据来源的字段。
- 重点展示客户名称、公司、联系人、电话、负责人、状态、来源、最近跟进时间、下次联系时间、合同到期时间和合同金额。
- 支持快速查看、编辑、添加跟进、查看时间线、转入公海和负责人变更。
- 对电话、邮箱等敏感字段按照权限显示，不能在无权限时通过前端接口或导出绕过限制。

#### 客户详情

- 将客户详情做成系统核心工作入口。
- 顶部显示客户名称、公司、状态、负责人、最近跟进、下次联系和合同状态。
- 使用标签页或明确分区展示：基本资料、跟进时间线、任务、合同备案、订单、回款、文件、公海流转记录。
- 跟进时间线必须显示联系类型、内容、结果、下一步行动、附件、创建人和时间。
- 常用操作固定在明显位置：新增跟进、安排下次联系、创建任务、上传合同、查看订单、查看回款。
- 危险操作单独分组，并要求二次确认和填写原因。

#### 电销名单和销售线索

- 维持现有字段和现有录入方式。
- 清楚区分“电销名单来源”和“销售线索业务对象”。
- 支持查看联系次数、最近联系时间、状态、结果、是否有效、负责人和关联客户。
- 转换为客户时保留原始名单/线索记录、来源、负责人和转换时间。
- 批量导入必须先预检，再展示重复、缺失和格式错误，不允许导入失败后只显示一句笼统错误。

#### 公海池

- 清晰展示客户名称、进入公海时间、进入原因、原负责人、当前状态、可认领状态和最后跟进时间。
- 认领前显示当前用户剩余认领额度。
- 认领、分配、收回、转移和自动回收均要显示明确的业务提示、权限提示和操作结果。
- 展示公海流转历史，至少包括操作人、操作时间、原负责人、新负责人、动作和原因。

#### 合同、订单、回款和发票

- 使用一致的金额格式、日期格式、状态标签和关联客户入口。
- 明确显示订单金额、已收金额和未收金额，不允许使用多个口径重复计算。
- 收款录入前校验订单状态、金额上限和重复提交。
- 合同版本必须可追踪，旧版本不能被无痕覆盖。
- 文件预览和下载必须经过服务端权限检查，不能直接暴露存储地址。

## 五、销售 SOP 业务流程

围绕现有字段建立以下可执行流程：

```text
电销名单
  → 联系记录
  → 有效线索
  → 分配负责人
  → 转入客户
  → 客户跟进
  → 安排下一次联系
  → 合同备案
  → 销售订单
  → 回款和发票
  → 客户维护、续签或重新进入公海
```

### 5.1 每个流程必须明确

- 谁可以发起
- 必填字段
- 可选字段
- 允许的状态变化
- 不允许的状态变化
- 需要谁的权限
- 是否产生提醒
- 是否产生任务
- 是否需要保留历史记录
- 出错时如何恢复
- 统计时使用哪个时间和金额口径

### 5.2 重点业务规则

- 电销名单转客户后保留原始记录，不删除来源数据。
- 线索和客户查重至少检查电话、邮箱、公司名称，编辑时排除当前记录本身。
- 客户只能有明确的销售负责人；负责人变更必须记录前后值和原因。
- 公海认领必须校验用户状态、权限、认领额度、客户当前状态和并发冲突。
- 自动回收必须有明确原因，并记录进入公海时间和回收规则。
- 跟进记录必须关联客户、负责人和联系内容；有下次联系时间时自动进入提醒列表。
- 订单金额必须大于零；收款金额必须大于零且不能超过订单未收金额。
- 有收款记录的订单不能直接删除，应改为取消、作废或其他经过确认的业务状态。
- 合同版本只能新增版本或标记最新版本，不能无痕覆盖历史文件。
- 删除业务数据前先判断是否存在关联记录；涉及合同、订单、收款、跟进和客户的记录优先使用停用、取消或归档。

## 六、校验与数据质量要求

### 6.1 前端校验

- 表单字段使用明确的必填、长度、格式、范围和提示信息。
- 电话、邮箱、日期、金额、文件大小和文件类型必须在提交前提示。
- 必填校验不能只依赖 placeholder，必须有清晰 label 和错误提示。
- 保存过程中禁用重复提交按钮，并展示保存中状态。
- 列表筛选、分页、排序和批量操作要保留当前条件。

### 6.2 服务端校验

- 所有写接口必须使用 Zod 或项目已有的强类型校验，不信任前端传入的数据。
- 服务端重新执行权限、数据范围、业务状态和关联关系校验。
- 接口返回统一的错误结构、HTTP 状态码和可读的中文提示。
- 对金额使用 Decimal 计算，不使用浮点数直接累计。
- 对创建收款、公海认领、负责人转移等操作增加幂等或并发保护。
- 导入接口返回逐行错误结果，不因为一行错误导致错误信息丢失。
- 防止越权读取、越权修改、越权导出和越权下载。

## 七、数据安全要求

- 认证继续使用当前 NextAuth，不在页面中自行判断登录后直接相信客户端字段。
- CASL 只作为前端体验辅助，服务端接口必须再次执行权限和数据范围判断。
- 明确区分功能权限、记录权限和字段权限。
- 普通销售默认只能查看本人客户；主管查看本人及下属；财务只查看必要的订单、合同、回款和发票信息；管理员维护系统权限。
- 电话、邮箱、微信、合同文件和回款信息必须按角色和数据范围保护。
- 下载合同、回款附件和客户文件时，服务端必须校验当前用户是否有权访问，再返回文件或签名地址。
- 日志中禁止记录密码、完整 token、数据库连接串和敏感业务正文。
- 高风险操作必须写审计记录：登录失败、用户停用、权限变更、客户导出、公海认领、公海回收、负责人转移、合同版本变更、订单金额变更、收款登记和文件下载。
- 业务删除默认采用软删除、停用、取消或归档，不直接破坏历史数据。
- 文件上传必须校验扩展名、MIME、大小和文件名，防止脚本文件伪装上传。
- 富文本和外部内容必须经过清洗，防止 XSS。
- 接口需要有合理的异常处理和限流边界，不把数据库错误、服务器路径和内部堆栈返回给用户。
- 生产配置和密钥只从环境变量读取，不能写入源码、日志、文档或提交记录。

## 八、工程实施要求

1. 先阅读项目结构、`prisma/schema.prisma`、认证、CASL、主要页面和 API，再形成现状审查记录。
2. 先列出问题，按 P0、P1、P2 排序；P0 是阻塞使用、安全、数据错误和金额错误，P1 是流程和体验改进，P2 是后续增强。
3. 只修改与 CRM UI、业务流程、校验、权限、安全和可维护性有关的文件。
4. 优先复用现有 Ant Design、React Query、Zod、ECharts、CASL 和 Prisma，不随意更换框架或引入新组件库。
5. 如果确实需要新增字段或数据库模型，先说明现有字段为什么无法满足，并给出迁移、回滚和历史数据兼容方案。
6. 动态语言代码文件尽量控制在 300 行以内；发现超长文件时，按领域拆成可理解的小模块，不进行无关重构。
7. 启动、测试、构建、停止和日志统一通过项目 `scripts/` 目录下的脚本执行。
8. 先补充或修复测试，再修改实现；每次修改后重新运行测试和构建。
9. 使用真实浏览器检查登录、客户列表、客户详情、新增跟进、公海认领、订单、收款、权限拒绝和文件下载流程。
10. 所有失败都要追到具体原因并修复，不能通过隐藏错误、硬编码成功数据或跳过校验来制造“通过”。

## 九、必须验证的场景

- 普通销售登录后只能看到本人权限范围内的数据。
- 主管可以查看本人及下属客户，但不能查看无权限的财务敏感字段。
- 财务人员可以登记合法收款，不能登记超过未收金额的收款。
- 未登录用户访问受保护页面和 API 必须被拒绝。
- 无权限用户不能通过修改 URL、请求参数、ID、导出接口或下载地址越权获取数据。
- 新增重复客户时得到明确提示，不能生成重复主档。
- 电销名单或线索转客户后，原记录仍然存在且来源可追溯。
- 公海认领达到额度时不能继续认领；两个用户同时认领时不能重复归属。
- 客户跟进设置下次联系时间后，提醒列表能正确显示今日、即将到期和逾期状态。
- 订单有收款记录时不能直接删除。
- 合同新建版本后旧版本仍然可追溯，未授权用户不能下载合同文件。
- 导入数据出现错误时能返回逐行错误，不影响已有正确数据。
- 页面在加载、空数据、错误、无权限和窄屏场景下不重叠、不溢出、不出现不可操作按钮。

## 十、运行和交付要求

优先使用以下项目脚本：

```powershell
python scripts\manage.py start
python scripts\manage.py test
python scripts\manage.py build
```

如果现有脚本缺少某个命令，先修复 `scripts/` 目录下的启动、停止、测试、构建和日志脚本，再继续验证。日志统一写入项目 `logs/` 目录。

完成后必须输出：

- 修改了哪些页面、组件、接口和数据校验
- 哪些现有字段被复用
- 哪些问题已经修复
- 哪些风险仍需客户确认
- 运行过哪些测试和构建命令
- 每条命令的真实结果
- 是否有数据库迁移、迁移前备份和回滚方案
- 是否有未完成项

不要声称“已完成”“已通过”或“已部署”，除非相关命令和真实页面流程已经执行并有结果记录。

## 十一、禁止事项

- 不把销售 CRM 改成调解系统、ERP、OA 或低代码平台。
- 不凭空增加客户没有要求的对象和字段。
- 不删除原始客户、线索、电销、跟进、合同、订单和回款数据。
- 不绕过现有认证和 CASL 权限体系。
- 不只改颜色和圆角而不修复流程、校验和错误状态。
- 不复制其他产品的 Logo、品牌颜色、页面截图、文案或受版权保护的素材。
- 不在客户端单独实现安全校验而忽略服务端校验。
- 不把数据库错误、密钥、token、密码和内部路径暴露给用户。
- 不用 mock 数据掩盖真实接口错误。
- 不新增没有必要的依赖，不在未检查 `package.json` 的情况下导入第三方库。

现在开始：先审查现有系统并输出当前问题清单，然后按 P0、P1、P2 逐步实施。每完成一个阶段都要运行验证脚本、检查真实页面，并自动修复发现的问题。
