# Proposal: crm-market-requirements-enhancement

## Why
现有 DOCX 准确记录了安全与工程整改，但仍像代码缺陷清单，缺少 CRM 产品主链路、市场基线、角色场景和当前完成度。本轮复审还发现“换语言”不能按偏好决定：现有项目约 15,179 行源码、34 个 API Route Handler、20 个页面，认证、CASL 权限和 Prisma 数据访问深度耦合。需要在需求文档中明确当前技术路线、跨语言候选、迁移成本和后续拆分触发条件。

## What
- 新建标题含“市场调研规划完善版”的 DOCX，保留原文档与原生成入口，并增加官方来源、适用范围和技术选型章节 | verify: 原 DOCX 与旧脚本未被覆盖，新 DOCX 可打开且包含来源清单
- 增加产品定位、角色、Lead-to-Cash 主流程及“已实现/部分实现/模型预留/未实现”矩阵 | verify: Task、DailyReport、Order、收款删除、用户/角色/消息/文件/设置均通过负向检查，断裂或 mock 模块不标为已实现
- 将整改项与市场能力重组为 P0/P1/P2/暂缓：P0/P1 写可执行验收，P2/暂缓只写进入条件、依赖和范围边界 | verify: PWA 位于 P1、AI 位于 P2，规划项均标记“规划/未实现”
- 增加技术选型结论：本轮继续 `TypeScript + Next.js + React + Prisma + MySQL` 技术族，按模块化单体演进；当前版本与 Next.js 15.4/React 19 目标版本分别标注，Java/Spring Boot、C#/ASP.NET Core、Python、Go 记录为条件触发的后续候选 | verify: 文档列出保留资产、重写边界、强制/综合触发条件和“暂不迁移”理由，不使用未经验证的性能排名或固定语言顺序
- 将 P0 技术整改写入需求：Service/Use Case、DTO/Zod、统一认证与数据范围、短事务、幂等、唯一约束、OCC/Serializable、旧 API 契约快照和契约测试 | verify: 34 个 Route Handler 形成方法/路径/请求/响应/状态码/错误及前端调用方基线；金额和权限路径有负向测试，响应标准化不静默破坏旧消费者
- 将 P1 技术治理写入需求：Prisma migration 规范、OpenAPI、审计日志、健康检查、结构化日志、有限工作流执行日志、共享缓存/队列边界 | verify: 文档要求 expand/contract、备份/回滚演练，覆盖 Decimal/枚举/Json/唯一约束/级联和文件旧对象访问；长任务不持有长事务
- 增加 Next.js 15.4/React 19 独立兼容升级要求，不在本文档中预设其与服务层整改的先后顺序 | verify: 后续升级验收包含 `next build`、NextAuth JWT/callback、登录态续期、受保护页面/API，以及列表/详情/导出/报表下钻的 CASL 与数据范围矩阵
- 补充非功能需求、指标口径、数据治理、集成边界、阶段顺序和精简追踪矩阵 | verify: 需求编号可追踪到代码证据、官方来源和验收项，不虚构日期、负责人或交付承诺
- 新增独立生成脚本并执行 DOCX 渲染与结构检查 | verify: 旧入口仍可运行；新文档页面 PNG 无截断/重叠，日志记录页数、章节和需求数量

**Not in this change**: 不修改 CRM 业务源码、数据库和现有接口；不整体迁移 Java/.NET/Python/Go；不承诺多租户、完整 CPQ/ERP、电子签、原生双端、离线同步、自主 Agent 或平台级低代码能力。

## How
- 采用“现状证据 + 官方市场实践 + 技术选型 + 分期范围”四栏逻辑，所有市场能力标明当前完成度。
- 以销售型 CRM 为边界：P0 先修认证、权限、数据质量、金额与审计；P1 补线索商机、活动、有限自动化、报表和响应式/PWA；P2 再评估辅助 AI。
- 技术实现继续采用 TypeScript/Next.js/React 技术族，并建立领域服务/use-case、DTO/Zod、统一授权和事务边界。Next.js 15.4/React 19 是后续目标基线，升级顺序由独立兼容性评估决定。
- 监管或客户合同要求独立安全边界、网络隔离、统一企业 SSO 时立即启动后端拆分评估；其余多客户端、独立扩容/队列、成熟平台和规模信号综合判断。触发后按团队、运维、合规和实测负载比较候选 PoC。
- 使用现有 DOCX 构建脚本生成独立新版本，延续黑色标题、正文固定 20 磅和 A4 版式，并在渲染后逐页复核。

## Risk
- 范围风险：市场功能过多会掩盖当前阻断缺陷；通过 P0/P1/P2/暂缓分层并将构建阻断项置顶控制。
- 选型风险：把“继续 TypeScript”误读为永不拆分；通过明确触发条件、PoC 和契约先行保留演进路径。
- 事实风险：厂商页面会更新或含营销表述；文档记录访问日期和官方 URL，旧版本页面只写成实践参考。
- 兼容风险：生成脚本或文档入口变化可能影响现有流程；新增独立脚本，旧入口和原 DOCX 保持不变。
- 可读性风险：长路径和大矩阵可能造成分页拥挤；通过附录集中证据、缩短正文引用和渲染复核修正。
- Rollback plan: 删除新 DOCX 和本变更新增的生成脚本即可回到当前文档，原版始终保留；技术选型章节可单独修订，不影响既有业务源码。
