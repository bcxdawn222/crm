# Proposal: crm-code-audit-and-flow-repair

## Why
上一轮修复了 CRM 的构建、认证、公海和收款页面阻断，但代码审查发现订单和任务仍有一段实际不可用：订单新增表单没有客户选项，任务新增表单没有负责人选项；两个页面还提交了 Prisma 中不存在的状态值；销售角色能看到创建任务按钮，却没有对应的 `task:create` 权限。结果是用户可以打开页面，但无法可靠地完成新增或筛选。

本轮只恢复现有订单和任务流程，不新增业务模块，不改变数据库表结构，也不删除任何客户、订单、任务或历史记录。实现以当前项目已有的 Next.js、React、Ant Design、Prisma、权限映射和接口为准。

## What
- 为订单客户选择框接入现有客户查询接口，支持首次加载、关键字搜索、加载中、空数据和失败提示。  
  verify: 打开订单新增表单能够加载当前用户数据范围内的客户；输入关键字后能够刷新选项；无客户、加载失败和未登录状态均有明确提示；客户量超过单页大小时不会把分页误当成全部数据。
- 修正订单页面的状态筛选和显示映射，只使用 `PENDING`、`CONFIRMED`、`DELIVERING`、`COMPLETED`、`CANCELLED`。  
  verify: 订单列表不会再请求 `PROCESSING`；每个状态筛选值都能通过服务端校验；非法状态返回明确的 `400`，不静默显示空列表。
- 在订单创建接口补充客户存在性、有效性和当前用户数据范围校验。  
  verify: 可访问客户能够创建订单；不存在、停用或越权客户不能创建；创建记录的销售人员仍来自登录用户，客户端不能通过修改请求体越权写入。
- 新增面向任务表单的窄权限负责人查询接口，不复用管理员专用的 `/api/users` 接口。  
  verify: 任务表单能够加载允许选择的 ACTIVE 用户；返回结果不包含密码、权限等敏感字段；销售只能看到自己，其他有权限角色只能看到其数据范围内的负责人。
- 修正任务创建接口的负责人范围校验，并处理销售角色的创建权限。  
  verify: 销售可以创建指派给自己的任务；销售不能把任务指派给其他人；主管、管理员、财务按各自数据范围选择负责人；越权负责人由服务端拒绝而不是依赖页面下拉框限制。
- 修正任务页面的状态筛选和显示映射，只使用 `TODO`、`IN_PROGRESS`、`COMPLETED`、`CANCELLED`。  
  verify: 任务列表不会再请求 `DONE`；状态标签和筛选项与 Prisma 枚举一致；非法状态返回明确的 `400`。
- 增加订单和任务新增流程的静态、接口和页面回归检查。  
  verify: 路由检查、类型检查、生产构建通过；在 MySQL 可用时完成客户选择、订单创建、负责人选择、任务创建、越权拒绝和空数据状态回归；测试日志写入 `logs/`，本轮临时文件在验证后清理。

**Not in this change**:
- 不新增数据库字段、表、枚举或迁移，不重写已有客户、订单、任务和历史数据。
- 不升级 Next.js、React、Prisma、Ant Design 或其他依赖，不新增表单库、状态管理库或用户目录服务。
- 不重构订单页和任务页的整体布局，不把本轮问题扩大为全站 UI 重做。
- 不新增任务委派、团队组织架构或复杂的跨部门数据范围模型。
- 不恢复收款硬删除，不修改上一轮已完成的认证、公海和收款边界。
- 当前目录没有 `.git` 时，不初始化仓库、不合并 `main`、不伪造提交。

## How
- 先对照 `prisma/schema.prisma` 中的 `OrderStatus`、`TaskStatus` 和当前接口契约，集中整理页面状态映射，避免继续散落不存在的枚举值。
- 订单客户选择复用 `GET /api/customers`，首次加载第一页，关键字变化时重新查询；保留现有客户数据范围、分页字段和错误响应，不在客户端复制客户数据权限。
- `POST /api/finance/orders` 保持现有入口，在创建前重新查询客户并校验当前用户是否有权访问，订单销售人始终取登录用户。
- 新增 `GET /api/tasks/assignees`，只返回任务表单真正需要的公开字段；接口按登录用户角色和数据范围返回 ACTIVE 负责人。销售默认只返回自己，主管、管理员、财务返回其允许范围内的人员。
- `POST /api/tasks` 保持现有入口，在写入前重新校验负责人存在、状态有效和负责人范围。销售创建任务时只允许 `assigneeId` 等于本人；页面也隐藏不必要的负责人选择，但服务端仍保留校验。
- 使用现有 `scripts/` 下的启动、类型检查、构建和冒烟入口记录验证结果。MySQL 未恢复时只报告静态验证通过和真实接口验证阻塞，不把模拟结果写成真实通过。

## Risk
- 销售只能创建自己的任务是本轮的升级决策。如果客户实际需要销售给同组成员派单，需要重新定义“同组”的组织关系和数据范围；在没有该定义前直接放开会扩大任务可见性。
- `/api/customers` 是分页接口，客户量较大时表单不会一次展示所有客户；通过关键字搜索解决可用性，后续如需远程滚动加载应另立需求。
- 订单和任务页面的显示文案可能与旧页面不同，但底层值会与现有 Prisma 枚举一致；历史数据不变。
- 真实业务回归依赖本机 MySQL 服务。服务若仍因 Windows 权限无法启动，代码可以完成静态检查，但登录、数据范围、并发和写入验证仍需标记为未完成。
- 当前依赖审计中的既有漏洞不在本轮处理；不执行强制升级，避免把安全依赖升级和业务字段修复混在同一变更中。
