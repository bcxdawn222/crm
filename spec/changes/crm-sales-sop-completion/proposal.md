# Proposal: crm-sales-sop-completion

## Why

现有 CRM 的客户、跟进、提醒、任务、合同、订单、回款和统计功能已经形成业务雏形。本次不再扩大销售功能范围，而是把现有流程的质量要求落到系统治理上，确保数据可追溯、异常可定位、备份可恢复、权限可验证、发布可回滚。

## What

- 编写并交付现有销售流程 PRD 与 Phase 实施计划，明确功能不变和非功能验收边界 | verify: `docs/` 存在 PRD，`discuss/` 存在 phase 计划，文档明确本期不新增销售业务功能。
- 增加结构化业务审计基础，接入客户、公海、订单、回款、合同和文件访问等关键路径 | verify: 关键操作产生审计事件，敏感字段被过滤，写入失败不会伪装成业务成功。
- 增加统一请求标识、服务端错误日志和安全错误响应 | verify: 失败响应只包含通用错误和 `requestId`，详细错误写入 `logs/`，不出现密码、令牌、服务器路径或堆栈。
- 增加数据质量、迁移、备份和运行状态检查，并接入 `scripts/` | verify: 检查发现问题时返回非零退出码；`python scripts\manage.py typecheck/routes/build` 均可执行并写日志。
- 不改变现有销售页面和字段语义，Phase 1 只实施治理基础 | verify: 现有路由契约检查通过，客户、跟进、提醒、订单、回款和统计页面未引入新的业务状态或流程入口。

**Not in this change**: 不新增商机、报价、产品目录、AI、ERP、原生移动端、复杂审批流；不升级 Next.js/React 大版本；不初始化 Git 仓库；不伪造线上角色验收或备份恢复通过结果。

## How

- 采用独立 `AuditEvent` 作为业务审计事实源，原有公海 JSON 历史继续兼容，不删除原始数据。
- 审计写入使用结构化输入和敏感字段过滤；关键业务写入与审计写入在同一数据库事务内完成，无法记录审计时拒绝宣称操作成功。
- 请求标识通过服务端统一生成或透传，错误响应只返回稳定的通用信息和标识，详细异常进入文件日志。
- 数据质量脚本默认只读；备份检查先校验压缩完整性和哈希，再进行可选恢复演练，不接触正式业务数据。
- 先完成本地类型检查、路由契约和构建，再进入线上迁移；线上迁移前必须已有可恢复备份。

## Risk

- 审计模型和迁移会增加数据库表及写入开销；通过只记录关键动作、建立对象/时间索引和短事务控制影响。
- 部分历史接口没有统一错误格式；本期只收敛新增治理入口和关键错误，不大范围重写旧响应，避免破坏既有页面。
- 业务数据为空或测试数据不足时，不能证明真实角色流程；报告必须标记“未验证”，不能用静态检查替代浏览器验收。
- 审计日志可能包含敏感字段；写入前按字段名过滤，并通过脱敏单测检查密码、令牌和附件凭据不落库。
- 回滚时先停用审计写入开关并恢复应用版本；已产生的审计事件不删除，数据库迁移只允许按已验证脚本回退。
