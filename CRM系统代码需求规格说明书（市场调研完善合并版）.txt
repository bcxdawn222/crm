文档状态：需求基线与规划文档；规划项不是当前已实现能力

一、结论摘要
当前项目最合适的主语言仍是 TypeScript。建议继续采用 TypeScript + Next.js + React + Prisma + MySQL 技术族，先把现有 Next.js 全栈代码整理为模块化单体；不立即整体迁移 Java、C#、Python 或 Go。
这不是对所有 CRM 项目的通用结论：从零建设大型企业 CRM 时，Java/Spring Boot 或 C#/ASP.NET Core 可能更适合；Python 更适合作为 AI/数据服务；Go 更适合作为高并发连接器和 Worker。
Next.js 15.4 与 React 19 是后续目标基线，当前代码仍是 Next.js 14 与 React 18，升级需要独立兼容验证。

二、当前系统与证据
1. 现有源码约 91 个 .ts/.tsx/.prisma 文件、约 15179 行，34 个 API Route Handler、20 个页面。
2. 33 个 API 文件直接访问 Prisma，33 个涉及认证，31 个涉及 CASL；源码约有 106 处 any。
3. Prisma schema 当前包含 User、Customer、Lead、FollowUp、Order、Payment、DailyReport、Task、Message、File、ContractArchive 等模型，但没有 tenantId/orgId。
4. Task、DailyReport、Order、收款删除存在接口/模型不一致或路由缺失；消息、用户、文件、设置存在 mock、只读或部分实现。
5. 当前不存在统一 service/repository/controller/dto/validator 分层、typed API client 或 OpenAPI 契约。

三、产品定位与主流程
定位：面向中小销售团队的销售型 CRM，不扩张为低代码平台、ERP 或完整 CPQ。
主流程：线索 → 客户/联系人 → 商机 → 报价/合同 → 订单 → 回款 → 活动与复盘。
角色：销售、销售主管、财务、管理员；功能权限与数据范围分离，数据范围覆盖本人、下属、部门、共享和全局。

五、技术选型复审
1. TypeScript + Next.js：当前项目成本最低，可保留 React/Ant Design 页面、Prisma schema、MySQL、NextAuth、CASL 和现有 API 路径。改进方向是抽 Service/Use Case、DTO/Zod、统一授权、事务、幂等和审计。
2. NestJS：当需要独立 API、队列、定时任务和多个客户端时，可作为 TypeScript 后端过渡；其队列和调度生态仍需 Redis、Worker 与独立运维。
3. Java + Spring Boot：适合大型企业后端、复杂审批、多组织、方法级授权和成熟 Java 运维体系，但需要重建认证、权限、ORM、迁移、部署和测试。
4. C# + ASP.NET Core：适合已有 Azure、Windows、Microsoft Identity 和 .NET 运维体系的组织；EF Core 事务和策略授权能力较完整，迁移成本与 Java 同级。
5. Python + Django/FastAPI：Django 适合后台管理，FastAPI 适合独立 API、AI 和数据服务；主 CRM 迁移需重建会话、权限、ORM 和类型约束。
6. Go：适合 Webhook、异步 Worker、连接器和高并发外围服务；主 CRM 的 RBAC、数据范围、工作流和后台管理需要大量自行组合。

六、推荐架构路线
近期：Next.js 页面与 BFF + 统一 Auth/Permission Service + Domain Service/Use Case + Prisma/MySQL。
中期：先冻结旧 API 契约，再按资源把服务层迁移到独立 TypeScript 后端；前端、数据库和对象存储优先复用。
长期：出现强制合规隔离、网络边界或统一企业 SSO 时立即评估后端拆分；多客户端、独立扩容、队列、成熟目标栈团队和单体规模瓶颈作为综合评估信号。触发后按团队、运维、合规和实测负载选择 PoC，不固定语言顺序。

七、分期需求
P0：认证数据源、权限与数据范围、公海认领并发、订单回款金额一致性、合同文件保护、密钥治理、构建阻断修复。
P1：Zod/DTO、API 契约快照、Prisma migration、审计日志、健康检查、结构化日志、有限自动化、报表口径、响应式/PWA、队列边界。
P2：确认式 AI 摘要、跟进草稿、风险提示和自然语言报表；默认不自动写入业务数据。
暂缓：多租户计费、完整 CPQ/ERP、电子签、原生双端离线同步、自主 Agent、平台级低代码。

八、工程验收要求
P0 验收：认证使用数据库用户且禁用账号被拒绝；销售/主管/财务/管理员权限矩阵通过；公海并发认领仅一人成功且配额准确；零值、负数、NaN、Infinity、超额收款被拒绝；未授权用户不能下载合同；密钥扫描无真实凭据。
P1 验收：34 个 Route Handler 形成方法、路径、请求、响应、状态码、错误和前端调用方快照；Zod/DTO 拒绝非法日期、枚举和分页；Prisma migration 覆盖 Decimal、枚举、Json、唯一约束和级联并完成 expand/contract、备份与回滚演练；文件旧对象访问、下载权限和签名 URL 回归通过；审计、健康检查、结构化日志、OpenAPI 和有限工作流日志可查询；长任务进入队列且不持有长事务。
版本验收：执行 next build；验证 NextAuth JWT/callback、登录态续期、受保护页面/API、CASL 数据范围、列表/详情/导出/报表下钻，升级前后关键业务结果一致。
P2/暂缓进入条件：P2 AI 依赖审计、数据脱敏、模型供应商、成本上限和用户确认写入；多租户依赖 tenantId/orgId 与隔离方案；原生离线依赖同步协议和冲突策略；低代码依赖对象元数据、脚本沙箱和生态治理。在依赖未满足前只保留规划，不标记为已实现。
负向状态：Task、DailyReport、Order、收款删除、消息、设置和 mock 模块必须保留“部分实现/模型预留/未实现”证据，不得在矩阵中标为已实现。

CRM 系统代码审查整改需求规格说明书
基于现有 Next.js、Prisma、NextAuth 与 CASL 实现的整改需求
说明：本文档依据当前工作区源码静态审查结果编制。由于项目依赖尚未安装，构建、类型检查与 lint 的最终结果标记为待验证。
1 文档目的与范围
本文档将代码审查发现的问题转化为可实施、可验收、可追踪的整改需求，用于后续排期、开发、测试和交付验收。整改对象为 CRM 系统的认证、授权、客户管理、公海池、订单收款、合同文件、运行脚本、日志、测试和代码结构。
本次范围以现有代码行为为依据，不把尚未实现的能力描述为已完成。页面视觉重设计、全新业务模块和生产部署架构不在本轮核心范围内；如实施过程中触发框架版本升级，应作为独立阶段验证。
2 当前系统理解
系统采用 Next.js App Router 同时承载页面与 API，Prisma 连接 MySQL，NextAuth Credentials Provider 负责登录与 JWT 会话，CASL 将权限码映射为操作能力，数据权限模块递归查询上下级关系。前端使用 React、TypeScript 与 Ant Design，合同备案文件当前保存到 public/uploads/contracts，并保留 OSS 工具代码。
3 审查依据与问题摘要
4 整改需求
REQ-01 统一认证数据源
需求说明：登录认证改为读取数据库用户，校验 bcrypt 密码、用户状态、角色和权限。会话中的 userId 必须来自数据库主键，移除运行时硬编码账号依赖。
验收标准：标准 seed 后可使用数据库账号登录；JWT userId 在 User 表存在；INACTIVE 与 LOCKED 账号登录被拒绝；不存在两套相互冲突的用户初始化流程。
REQ-02 统一权限模型与管理员能力
需求说明：定义唯一的权限码、动作和资源类型来源。管理员采用明确的 manage/all 规则或统一的管理员判定函数，前端、middleware 与 API 使用同一语义。
验收标准：管理员可访问其应有的合同查看、预览、下载和删除操作；未知权限码默认拒绝；权限单元测试覆盖四类角色和无角色用户。
REQ-03 集中数据范围授权
需求说明：建立可复用的数据范围策略，统一表达本人、下属团队、全局只读和全局管理。读取、更新、归档、转移、删除、下单和合同操作均在数据库查询条件中合并范围约束。
验收标准：销售仅操作本人数据；主管仅操作本人及下属数据；财务权限按业务动作限制；越权 ID 返回 403 或 404；所有写接口具备对应回归测试。
REQ-04 修复公海池认领与配额
需求说明：新增独立认领记录或 claimedAt 字段，配额统计以认领事件为准。配额检查与客户认领在同一事务内完成，并以 isPublic=true 作为条件更新，避免重复认领。
验收标准：同一客户并发认领仅一人成功；每日次数准确累加；达到上限后请求被拒绝；管理员角色判断使用小写数据库角色或统一枚举。
REQ-05 保证收款与订单金额一致性
需求说明：金额输入采用十进制定点校验，要求大于零且为有限值。收款创建、订单余额校验和金额更新采用事务与条件更新；合同金额不得低于已收金额。
验收标准：零值、负数、NaN、Infinity、超额收款和合同金额低于已收金额均返回 400；并发收款后 paidAmount + unpaidAmount 始终等于 contractAmount。
REQ-06 建立 API 输入模型
需求说明：为请求体、查询参数、枚举、日期和分页建立 Zod 强类型模型。分页默认值和上限统一，错误响应使用稳定错误码。
验收标准：业务 API 不再直接信任未解析 JSON；page 大于等于 1，pageSize 设置合理上限；非法日期和枚举返回 400；核心 API 不使用未经批准的 any。
REQ-07 保护合同文件与上传边界
需求说明：受保护合同文件移出 public 静态目录，通过鉴权 API 流式返回或使用短时 OSS 签名地址。上传同时校验扩展名、MIME、文件签名、大小和规范化文件名。
验收标准：未登录用户持有文件路径时也取不到文件；PNG/JPG 合同不绕过鉴权；伪造 MIME、路径穿越文件名和超限文件被拒绝；删除备案同步处理存储文件。
REQ-08 密钥与错误信息治理
需求说明：轮换数据库密码、NEXTAUTH_SECRET 和加密密钥；仓库及交付包仅保留脱敏示例。客户端错误不返回数据库、堆栈或本机路径，详细异常写入文件日志并携带 requestId。
验收标准：交付扫描不出现真实密码或固定生产密钥；500 响应只包含通用信息和 requestId；服务端日志可通过 requestId 定位完整异常。
REQ-09 统一初始化与数据迁移
需求说明：确定唯一 seed 入口，角色、权限、演示用户和层级关系使用幂等初始化。可能清空业务数据的脚本标记为开发专用并加入显式确认参数。
验收标准：连续执行两次 seed 结果一致；不会因为用户 ID 策略导致外键错误；默认运行流程不会清空已有业务数据。
REQ-10 补齐 Run、Debug 与文件日志
需求说明：在 scripts 目录提供 start、stop、test、build、seed 和 export 的 .py 与 .sh 入口，Windows 默认使用当前 Python 解释器组织 npm 命令。应用日志统一写入 logs 目录并按日期或大小滚动。
验收标准：通过 python scripts\manage.py start|stop|test|build 可执行标准流程；对应 shell 入口行为一致；失败时返回非零错误码并在 logs 产生记录。
REQ-11 建立自动化质量门禁
需求说明：补齐单元测试、API 集成测试和关键角色 E2E 测试，测试重点覆盖认证、权限矩阵、公海池并发、收款一致性和合同下载。构建前必须完成依赖安装与 Prisma Client 生成。
验收标准：scripts 测试入口依次执行类型检查、lint、单元测试和构建；P0 场景均有回归用例；测试报告写入 logs 或标准测试报告目录。
REQ-12 拆分大文件并强化类型边界
需求说明：把页面拆为查询 hooks、表格列、表单、弹窗和领域类型模块；API 使用 Prisma 输入类型和显式 DTO，删除重复映射与无意义透传。
验收标准：动态语言代码文件尽量控制在 300 行以内；目录每层尽量不超过 8 个文件；新增代码无循环依赖，重复权限与映射逻辑有唯一实现。
REQ-13 技术栈基线适配
需求说明：在安全与数据一致性整改稳定后，单独评估并实施 Next.js 15.4、React 19 的兼容升级。升级按依赖逐项验证，不与核心业务修复混合提交。
验收标准：升级前后关键业务回归一致；阅读迁移说明并记录破坏性变更；锁文件与构建产物由标准脚本验证。
